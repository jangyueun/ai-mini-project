# 2일차 구현 및 확인 기록

## 무엇을 개선했나

기존 프로그램에는 SQLite 저장 기능이 있었지만, 실행 스크립트가 DB를 삭제하고 화면 새로고침 시 대화 ID도 바뀌었습니다. 또한 이전 대화를 불러와도 장애 조사 계획에는 이전 조사 대상이 전달되지 않았습니다.

이번 변경은 **저장된 대화를 다시 열고, 직전 조사 대상을 확인하여 새 상태로 재진단하는 것**에 집중합니다. RAG나 자동 복구 기능을 추가한 프로젝트는 아닙니다.

## 변경 구조

| 위치 | 역할 |
|---|---|
| `sh/run_agent_ollma.sh`, `sh/run_agent_openai.sh` | 기동 시 DB 삭제 제거 |
| `agent/session_store.py` | 기존 DB 보존·열 추가, 완료 대화·처리 이벤트·조사 대상의 원자적 저장, 선택 대화 삭제 |
| `agent/conversation.py` | 후속 요청·명시적 대상·모호한 대상·확인 질문 답변 처리 |
| `agent/graph.py` | 진입점에 `resolve_context` 노드 추가, 확인 필요 시 조회 없이 종료, 확정 대상 게이트 |
| `server.py` | 대화 조회·삭제 API, POST/SSE의 공통 맥락 입력·저장, 같은 대화의 동시 요청 제한 |
| `web_demo_server.py` | 조회·삭제 API 중계 |
| `web_chat.html` | 대화 ID 유지, DB 복원, 대화 선택, 새 대화, 삭제 확인, 후보 서비스 버튼 |

### 저장 흐름

1. 브라우저에는 대화 ID와 목록 제목만 저장합니다.
2. 메시지·조사 대상·확인 대기는 서버 SQLite에 저장합니다.
3. 새로고침하면 동일 ID로 서버에서 완료 메시지와 처리 단계를 가져옵니다.
4. 새 대화는 새로운 UUID를 사용합니다. 기존 기록은 삭제하지 않습니다.
5. 삭제는 사용자가 확인한 현재 대화의 메시지와 맥락에만 적용됩니다.

### 후속 요청 흐름

- `payments-service CPU 급증 원인 진단해줘` → 실제 수집한 대상 저장
- `그 서비스 다시 확인해줘` → 대상 하나면 복원하여 **새 MCP 호출** 실행
- 직전 대상이 복수면 서비스 선택 요청 → 서비스명 버튼/입력 → 원래 재조회 요청 실행
- 새 대화·직전 대상 없음 → 대상 확인 요청, `auth-service`로 임의 대체하지 않음
- 새 서비스가 명시되면 명시한 대상 우선
- 등록되지 않은 서비스는 조회하지 않고 확인 요청
- 맥락에는 이전 CPU·메모리 수치를 저장하지 않음. 과거 답변은 기록으로만 복원

## 기술 요소

- **LangGraph**: 기존 조사·작성·검증 흐름 앞에 맥락 해석 노드와 조건부 분기 추가
- **MCP**: 확정된 대상의 현재 샘플 상태를 새로 조회. 기존 Tool·Resource·Prompt 활용
- **SQLite**: 완료 메시지와 구조화한 맥락을 같은 트랜잭션으로 저장, 기존 DB 마이그레이션
- **FastAPI / Vue / SSE**: 대화 조회·명시적 삭제·복원·실시간 응답
- **LangSmith**: `resolve_context_node`를 포함한 그래프 기록. 모델 호출은 기존 모델 사용
- **모듈화·의존성 주입**: 순수 대상 해석 함수, 저장소 분리, 테스트용 모델·MCP·DB 교체
- **단위·통합·브라우저 테스트**: 모델의 우연한 답변과 독립적으로 저장·대상 선택 검증

## 재현 방법

기본 실행은 프로젝트 README의 Ollama 방식과 같습니다.

```bash
bash sh/run_agent_ollma.sh
# 두 번째 터미널
bash sh/run_frontend.sh
```

브라우저: <http://localhost:8600>

자동 테스트(외부 API 호출 없음):

```bash
.venv/bin/python3 -m unittest discover -s tests -v
```

고정 입력 비교의 개선 후 결과 재생성:

```bash
.venv/bin/python3 eval/compare_conversations.py --root . --output eval/after.json
```

개선 전은 첫 커밋 `5c6b9a0`을 별도 임시 폴더에 추출하고 같은 평가 스크립트의 `--root`로 지정합니다. 실제 작업 폴더를 이전 버전으로 되돌릴 필요가 없습니다.

브라우저 검증은 Node.js, `playwright`, 설치된 Chrome이 필요합니다. 사용 환경에 따라 `NODE_BINARY`, `NODE_PATH`를 지정하고 실행합니다.

```bash
.venv/bin/python3 eval/run_browser_checks.py
```

실제 모델 검증(실행 중인 Ollama 서버에 초기·후속 요청 2회):

```bash
.venv/bin/python3 eval/verify_local_model.py
```

## 한계 및 트레이드오프

- 한국어의 명시적인 재조회 표현과 등록된 서비스명 중심입니다. 별칭·복잡한 대명사·“첫 번째 서버” 등 자유로운 표현은 추가 지원이 필요합니다.
- 오래된 대화라도 직전 대상 이름은 유지됩니다. 단, 상태는 매번 새로 조회하며 모니터링은 실제 서버가 아닌 샘플 데이터입니다.
- 대상이 여러 개면 확인 과정이 한 번 더 필요하지만 잘못된 대상을 임의로 선택하는 것을 줄입니다.
- 화면은 최근 완료 메시지 최대 200개, 일반 대화 모델 입력은 최근 20개만 불러옵니다. 오래된 전체 기록 탐색/요약 기능은 없습니다.
- 완료되지 않은 요청의 재개·중간 토큰 복구는 지원하지 않습니다. 실패한 요청은 저장하지 않습니다.
- 같은 대화의 요청 제한은 현재 단일 서버 프로세스 범위입니다. 여러 worker 운영에는 공유 잠금이 필요합니다.
- 브라우저 저장소를 지우면 대화 목록을 잃습니다. 로컬 사용용으로 인증·사용자별 접근 제어가 없습니다.
- 기존 답변 검수는 길이·번호 형식 중심이며, 수치·주장 전체의 사실성을 보장하지 않습니다. 검수 고도화는 이번 범위 밖입니다.
- 같은 브라우저의 여러 탭은 선택한 대화 ID를 공유할 수 있습니다. 독립 대화가 필요하면 새 대화를 시작합니다.

실모델의 예시 답변에는 실제로 수행하지 않은 로그 분석이나 조치 이력을 암시하는 표현이 포함될 수 있습니다. 이번 기능은 대화 맥락과 재조회 대상을 보장하며, 생성된 답변 전체의 사실성 검증이나 서버 조치 실행 기능은 제공하지 않습니다.
