# 대화 연속성과 답변 수치 검증 최종 구현

## 발견한 문제

실제 Ollama 답변에서 현재 CPU가 88.4%인데도 90%를 초과한 상태라고 설명했습니다.
기존 validator는 30자 이상 및 `1)` 포함 여부만 검사했고 세 번째 실패 후에는 강제 합격했습니다.
대화 대상을 올바르게 고르는 것만으로 답변의 수치 해석까지 정확해지는 것은 아니었습니다.

## 추가 구현

- `agent/validation.py`: 조사에 성공한 서비스별 CPU·메모리와 초안의 인용값을 대조합니다.
- 현재 값, 알림 원문, 매뉴얼의 조건 표현을 구분하고 지원하는 초과·이상·미만·이하 비교를 계산합니다.
- 해당 서비스에 연결되지 않은 수치, 빠진 CPU·메모리, 조회하지 않은 서비스와 일부 근거 없는 로그 분석 단정을 반려합니다.
- `graph.py`: 오류 이유를 작성 모델에 전달해 재작성합니다. 총 3회 작성 후에도 실패하면 강제 합격하지 않고 코드가 만든 조회 근거 안내로 종료합니다.
- 장애 진단 초안은 검수 전 토큰 전송을 하지 않습니다. 일반 대화 스트리밍은 유지합니다.
- 화면과 저장 기록에 합격·재작성·실패를 구분합니다. 과거 기록은 이전 버전 검수임을 표시합니다.
- Ollama와 OpenAI 작성 프롬프트에 같은 작성 규칙을 적용했습니다. 실제 모델 검증은 Ollama로 수행하며 OpenAI API는 호출하지 않습니다.

## 검증 및 비교 조건

`eval/validation_cases.json`의 고정 초안 20개(오류 13개, 정상 7개)와 같은 모니터링 근거를 두 검수기에 제공합니다.
기존 조건은 이전 커밋 `e33a5d7`의 `len(draft)>=30 and "1)" in draft`입니다.
모든 평가 초안이 기존 형식을 만족하므로 기존 검수는 오류를 차단하지 못합니다.

| 항목 | 기존 형식 검수 | 개선 근거 검수 |
|---|---:|---:|
| 오류 초안 차단 | 0/13 | 13/13 |
| 정상 초안 통과 | 7/7 | 7/7 |

개발·회귀 검증용 소규모 고정셋입니다. 독립적인 자연어 벤치마크, 실제 LLM 생성 정확도 또는 응답 시간 개선을 측정한 수치가 아닙니다.
`validation_comparison.json`에 초안별 기대 판정·실제 판정·사유·데이터셋 해시를 보존합니다.
캡처 원본은 `doc/evidence/validation-comparison.html`, 브라우저 캡처는 `validation-comparison.png`입니다.

```bash
.venv/bin/python3 -m unittest discover -s tests -v
.venv/bin/python3 eval/compare_validation.py
.venv/bin/python3 eval/check_boundaries.py --root . --output /tmp/boundary-result.json
```

59개 자동 테스트 통과. 기존 대상 선택 경계 시나리오 24/24, 후속 요청 10/10과 기능 확인 16/16도 재실행해 유지했습니다.
새 테스트는 잘못된 수치·지표 교환·서비스 간 수치 교환·경계 비교·근거 없음·정상 표현을 포함하며,
실제 Graph/API/SQLite에서 재작성 피드백·3회 실패 대체 응답·미검수 초안 미전송·저장과 후속 대상 유지도 검사합니다.

## 실제 로컬 모델 확인

`eval/validation_live_results.json`은 qwen3:0.6b / qwen3:8b로 실행한 결과입니다.
3회 재작성 후 미조회 로그 분석 단정 등이 남아 검증 실패로 종료했고, CPU 97.3%·메모리 58.1%의 조회 근거 안내만 저장했습니다.
중간 초안에는 지원하지 않는 비교 표기로 인한 보수적 반려도 있었습니다. 이 결과를 모델 정확도나 모든 반려의 정당성으로 해석하지 않습니다.
실제 화면 캡처 `validation-live-final.png`는 별도 브라우저 요청의 결과이며 해당 대화 ID와 응답도 기록했습니다. 브라우저 요청에서는 CPU 94.2%·메모리 56.6%를 인용했고, 로그 조회 근거 없는 초안을 1회 재작성한 뒤 수치 검수를 통과했습니다. 원인·지속시간 등 전체 문장 사실성을 통과시킨 의미는 아닙니다.

Ollama의 사용자 대면 생성에는 `think: false`, `num_predict: 1024`를 적용해 생성량을 제한했습니다.
출력 길이 제한으로 답변이 잘리더라도 같은 검수를 거칩니다. 재작성 최대 3회 및 호출별 타임아웃이 있으므로 전체 응답 시간을 보장하지는 않습니다.
옵션의 공식 명세: https://github.com/ollama/ollama/blob/main/docs/openapi.yaml

## 한계와 트레이드오프

- 검사 범위는 서비스별 CPU·메모리 수치 인용과 지원 비교 표현입니다. 원인 분석·조치 적절성·모든 로그 주장과 모든 자연어를 검증하지 않습니다.
- 복잡한 표·부정문·별칭 등 지원하지 않는 표현은 정상 내용도 반려할 수 있습니다. 실제 모델에서 발견한 일부 표기 형식은 회귀 테스트로 보강했습니다.
- 최소한 서비스별 CPU·메모리 값을 모두 적도록 요구합니다. 짧은 답변을 원하더라도 재작성할 수 있습니다.
- 재작성은 모델 호출과 대기 시간을 늘리고, 미검수 토큰을 숨기므로 최종 답변이 나오기까지 기다려야 합니다.
- 고정 20개 사례의 성공은 일반적인 사실성 보장이 아닙니다. 모니터링은 여전히 샘플 데이터입니다.
- 전체 자유 문장 분석보다 검증된 구조화 관측값과 생성 설명을 분리하는 방식, 더 다양한 미사용 표현 평가가 다음 개선 과제입니다.

대화 보존·복원·분리, 확인 대기, 취소·제외, 새 MCP 조회는 기존 개선 범위 그대로 유지합니다.

## 사용자 확인 중 추가한 회귀 수정

2026-10-22 12:32 캡처에서 현재 CPU 90.8%를 적고도 “알림에 기록된 CPU 91%를 넘는 상태”라고 한 답변이 통과했습니다. 알림 인용 허용 분기가 비교 검사를 건너뛰는 문제였습니다. 현재 값에 대한 비교를 먼저 검사하도록 순서를 수정했습니다. 90.8%·91%에서는 반려하고 92%에서는 허용하며, 알림 수치의 단순 인용은 유지하는 회귀 테스트를 추가했습니다. 고정 20개 평가와 별도로 실제 캡처 문장의 반려 사유를 `eval/validation_alert_regression.json`에 기록했습니다.

실제 모델 재확인 중 `CPU 91% (threshold 80%)를 초과`라는 괄호 표기도 발견해 비교 검사에 포함했습니다. 동일 실제 생성문을 최종 검수기에 다시 넣었을 때도 반려하는지 확인했습니다. 원본 실행 기록과 최종 재검사 결과를 분리해 기록했습니다.
